# AI 辅助编程指导与迭代过程

## 1. 协作目标与角色分工

本项目依据《自动编程作业(1).docx》完成两项机器人编程作业，并按照课程要求经历题目理解、架构分析、方案审查、代码实现、运行验证和版本迭代。

在协作过程中，我负责提出任务、限定实现范围、审查方案、决定是否开始实施、运行程序并提出改进要求；AI 根据我的指令分析架构、提出方案、编写代码和 Markdown 文档，并执行基础测试。本文中的引用内容是我用于指导 AI 的指令，后续文字用于说明这些指令怎样落实到项目中。

## 2. 第一阶段：先理解代码框架

我首先指导 AI：

> 你现在查看我的代码，先分析代码框架后为我解释该代码用途。

我没有要求 AI 直接开始编码，而是要求它先阅读作业题目和基础代码，解释现有模块的作用。经过分析，确认基础工程包括：

- `env.py`：定义 5×5 网格、起点、终点、障碍物和动作规则。
- `planner.py`：使用 BFS 搜索从当前位置到终点的最短网格路径。
- `main.py`：创建环境、调用规划器并输出结果。

这一阶段还明确了现有代码只会生成 `up/down/left/right` 网格动作，尚不具备机器人朝向、动作翻译、自主执行和记忆功能。先分析再编码，可以避免把所有功能集中在主程序中，并为后面的模块划分提供依据。

## 3. 第二阶段：审查第一题方案

理解框架后，我继续指导：

> 现在你从第一题出发给出相应解决方案，由我审查，充分考虑代码实现的合理性。

AI 根据要求先提交方案，没有立即修改代码。第一题方案将“绝对网格动作”和“机器人相对动作”分为两个层次：

1. 保留 BFS 输出的网格动作。
2. 新增 `translator.py`，维护当前朝向，把每个网格动作翻译为转向指令和 `forward`。
3. 新增独立的 `Robot` 执行器，根据朝向执行机器人指令。
4. 使用两个独立环境分别执行网格动作和机器人动作，比较最终位置。

我审查这一思路时关注模块职责是否清楚、朝向是否随转动持续更新、180° 转向如何处理，以及验证过程是否独立。最终确定转换器负责翻译、执行器负责改变状态，避免用翻译逻辑自身验证翻译结果。

## 4. 第三阶段：聚焦第二题并参考第一题

随后我提出：

> 你现在聚焦第二题给出方案，可以考虑第一题是否存在思路参考，给出后由我审查。

第二题沿用第一题中“规划与执行分离”的思想，把流程扩展为：

```text
感知 → 规划 → 行动 → 记忆 → 下一轮
```

AI 提议新增：

- `agent.py`：组织完整循环，每轮读取环境、规划并执行动作。
- `memory.py`：记录步号、执行前位置、动作和执行后位置。
- `env.step()`：负责合法移动、碰撞处理和步数统计。

审查时重点确认：规划器不能直接修改环境；记忆必须保存实际执行结果；无解、起点即终点和步数上限必须有明确行为；默认地图需要用 8 步到达 `(4,4)`。

## 5. 第四阶段：部署代码并完成基本测试

方案通过后，我下达实现指令：

> 现在进行代码部署，只做基本测试，Markdown 编写后交付给我。

AI 按两个独立作业目录落地代码，同时编写需求、架构、运行说明和验证文档，并提供 `run.ps1` 与 `run.sh`。初次交付完成的主要功能是：

- 第一题将 8 个网格移动翻译为 10 条机器人指令，并验证两种执行方式均到达 `(4,4)`。
- 第二题完成自主循环，用 8 步到达 `(4,4)`，记录 8 条动作和包含起点的 9 个轨迹位置。
- 基本测试覆盖默认场景、无解、非法输入、碰撞、起点即终点和记忆重放。

这里的“部署”指在课程项目目录中完成代码组织、运行入口和本地验证，不指发布到服务器或真实机器人。

## 6. 第五阶段：先审查逐步地图方案，再实施

初版只能显示动作列表和最终地图。为了观察运行过程，我提出：

> 现在我要求将每走一步的当前轨迹也像最后一样以地图呈现，你先给出方案。

AI 先给出符号和接口方案：`A` 表示当前位置，`S` 表示起点，`*` 表示已走轨迹，`G` 表示终点，`#` 表示障碍，`.` 表示未走空地；先显示初始地图，再在每一步执行并写入记忆后显示累计轨迹。

我审查方案后下达“开始”指令。实现中由环境负责绘制地图，由智能体提供行动后的回调，由主程序负责终端输出。这样增加展示功能时没有把打印逻辑写入规划器或记忆模块。验收结果为初始地图 1 张、逐步地图 8 张，共 9 张地图。

## 7. 第六阶段：进行版本迭代

完成基础功能后，我继续指导：

> 现在这份代码还能做什么样的优化？

在审查可选优化方向后，我同意开始迭代：

> 你先按照尝试进行迭代。

### 7.1 第一轮：BFS 和智能体运行效率

第一轮保留所有外部行为，修改内部实现：

1. BFS 从“队列携带并复制完整路径”改为“记录父节点，找到终点后回溯”。
2. Agent 缓存尚未执行的路径，静态地图不再每走一步都重新搜索。
3. 每步执行前仍根据最新感知验证下一位置；缓存失效时重新规划。
4. 增加规划次数、展开节点数和发现节点数统计。

默认地图的规划调用从 8 次下降为 1 次，移动结果仍为 8 步到达终点。新增动态障碍测试，在原路径被阻断时验证智能体能够重新规划并绕开障碍。

### 7.2 第二轮：考虑朝向的最少指令规划

第一轮通过后，我同意继续进行朝向优化。第二轮保留题目要求的基础翻译流程，并新增进阶的 `robot_planner.py`：

- 搜索状态从位置扩展为 `(位置, 朝向)`。
- 搜索边直接使用 `forward`、`turn_left` 和 `turn_right`。
- 每条指令成本均为 1，BFS 求最少机器人指令数。

基础方案先向上再向右，需要 8 次前进和 2 次转向，共 10 条指令。优化方案先向东前进 4 格，再左转向北前进 4 格，共 9 条指令。由于曼哈顿距离要求至少前进 8 次，且初始朝向为东、目标还位于北方，至少需要一次转向，因此 9 条已经达到理论下界。

## 8. 第七阶段：归档文档并准备打包

最后，我提出：

> 现在归档 Markdown 文件，说明代码编程迭代过程。现在准备进行 Markdown 总结和项目打包。

归档采用以下结构：

```text
README.md                      项目入口和运行方法
docs/AI编程指导过程.md         我的指导、方案审查与迭代过程
docs/设计与验收说明.md         需求、架构、算法及最终验收结果
docs/terminal_log.md           本机终端运行记录
docs/archive/                  各阶段原始 Markdown 文档
```

这种组织方式保留原始过程证据，同时提供两份便于教师审阅的主文档。完整终端日志单独存放，避免使设计说明过长。

## 9. 最终结果与反思

最终项目满足两道题目的基础要求，并增加逐步地图、路径缓存、搜索统计、动态障碍重规划和朝向感知的最少指令规划。当前自动测试共 11 项，全部通过。

本次指导过程体现了以下方法：先理解现有代码，再分别审查两题方案；方案通过后实施基础功能；根据本机输出提出可视化需求；在结果保持正确的前提下分轮优化；最后整理文档和运行证据。这样的过程将需求、设计、实现和验证联系起来，也便于后续通过 Git 进行更细的版本管理。

## 10. 本地 Git 管理过程

代码和文档完成后，我要求检查并使用本机 Git 管理项目。Git 安装完成后，在项目目录初始化本地仓库：

```powershell
git init -b main
git add .
git commit -m "Complete embodied AI programming assignments"
```

第一次本地提交保存完整的作业代码、运行脚本、题目文件和 Markdown 文档，对应提交：

```text
6de02a2 Complete embodied AI programming assignments
```

随后，为了便于同一课程仓库继续存放其他作业，我要求把本次作业整体归入 `homework1` 文件夹。移动后先运行测试，再使用 Git 暂存全部路径变化：

```powershell
git add -A
git commit -m "Organize assignment under homework1"
```

第二次本地提交为：

```text
5810e33 Organize assignment under homework1
```

Git 将这次变化识别为 25 个文件的路径重命名，文件内容没有随目录整理而改变。完成后的本地仓库结构为：

```text
Embodied_AI_Course/
├─ .git/
└─ homework1/
   ├─ 模块1/
   ├─ 模块2/
   ├─ docs/
   ├─ README.md
   ├─ run.ps1
   └─ run.sh
```

本地 Git 记录用于查看每轮提交、比较文件变化和在需要时回到已验证版本。Markdown 中的过程说明用于解释设计思路，两者作用不同；实际版本状态应以 `git log` 和 `git status` 为准。
